# Voice Agent Design

Covers the real-time voice pipeline (`backend/app/voice/`) and prompt design (`backend/app/prompts/system_prompt.py`). See [architecture.md](architecture.md) for how a call reaches the pipeline in the first place, and [research-flow.md](research-flow.md) for the pricing/negotiation math the tools call into.

## Two agent modes

Both modes share the same pipeline builder (`_run_pipeline` in `app/voice/pipeline.py`) and the same 12 tools; only the system prompt, first message, and whether `property_id` is fixed differ.

| Mode | Entry point | System prompt builder | Scope |
|---|---|---|---|
| **Guest Support** | one property's `exophone` | `build_system_prompt` | Fixed to one `Property`; `recommend_properties` is explicitly disabled in the prompt (would surface unrelated properties). |
| **Lead Agent** | host's portfolio-wide `User.lead_exophone` | `build_lead_system_prompt` | No property pre-selected; qualifies the guest and recommends across the host's full portfolio via `recommend_properties`, then "locks" onto whichever property the guest shows interest in. |

Both browser-test variants (`run_browser_voice_pipeline`, `run_browser_lead_pipeline`) exercise the identical code path over WebRTC instead of Exotel, using a fixed placeholder identity `BROWSER_TEST_CALLER_NUMBER` for the guest.

### Property "locking" in Lead Agent calls

`app/voice/conversation_state.py` — a plain dataclass, `ConversationState(selected_property_id, selected_property_name)`, tracked programmatically alongside the LLM's own context rather than trusting the model to keep re-supplying a `property_id`. `lock_property()` is called from `check_calendar`, `get_pricing`, and `negotiate_rate`'s tool wrappers whenever they run. `recommend_properties` and `search_faq` both read `state.selected_property_id` as a fallback/guard:
- `recommend_properties` refuses to re-run with no new criteria once a property is locked (returns a natural-language redirect instead of calling the DB).
- `search_faq`'s `faq_property_id` fallback chain is: LLM-supplied arg → `state.selected_property_id` → the call's own fixed `property_id` (Guest Support) → `None` (portfolio-wide).

Guest Support calls never touch this — `property_id` is already fixed before the pipeline is built.

## Pipeline stages

`_run_pipeline` (`app/voice/pipeline.py`) builds a pipecat `Pipeline`:

```
transport.input() → SarvamSTTService → SilenceWatchdogProcessor → LanguageSyncProcessor → ConversationStyleProcessor
  → user_aggregator → RedundantContextGuardProcessor → StatePromptSyncProcessor → LLM → slow_tool_filler
  → RepetitionGuardProcessor → MetaCommentaryGuardProcessor → StyleComplianceMonitor → PropertyRecommendationGuardProcessor
  → EscalationPhraseGuardProcessor → PrematureEndCallGuardProcessor → ResponseShapeValidatorProcessor
  → EndCallReliabilityGuardProcessor → SarvamTTSService → transport.output() → assistant_aggregator
```

Nine of these (`RedundantContextGuardProcessor` through `EndCallReliabilityGuardProcessor`, excluding `StatePromptSyncProcessor` and `StyleComplianceMonitor`) are code-level backstops for confirmed-live prompt-compliance failures — `GOLDEN_RULES` states the rule, the processor is what actually guarantees it holds regardless of what the model does. All are inert (pass-through, no added latency) on the overwhelming majority of turns; each only activates around the specific narrow condition it exists for. `StyleComplianceMonitor` is the one exception to "guard" framing — it never rewrites or cuts anything (see below).

**Streaming discipline (response output architecture redesign)**: every processor from `RepetitionGuardProcessor` through `ResponseShapeValidatorProcessor` streams `LLMTextFrame`s through immediately as they arrive from the LLM — none of them buffer a full response before deciding whether to forward it. This replaced an earlier design where several of these buffered the entire response unconditionally on every turn (added latency on every single turn, not just violating ones) — see `ResponseComplianceProcessor`'s removal, below. Each processor still has full authority to stop forwarding the remainder of one response the instant it detects a real violation (repetition, a leaked `property_id`, a structural shape violation) — the accepted tradeoff is that the guest may hear one sentence before a guard reacts, never that a normal turn pays a buffering tax.

### Conversation architecture: three separate concerns, not one state blob

`app/voice/conversation_state.py`, `app/voice/conversation_style.py`, and `app/voice/conversation_quality.py` each own a distinct, non-overlapping slice of "what does the pipeline know about this call" — deliberately kept as three types, not one, so a component that only needs one slice (e.g. a future `PricingValidator`) can depend on a narrow type instead of the whole call state:

- **`ConversationState`** (facts) — what's known/happening: locked property, slots (`check_in`/`check_out`/`num_guests`/etc.), recommendations shown, escalation flag, closing state, conversation goal. Read by tool wrappers and `StatePromptSyncProcessor`.
- **`ConversationStyle`** (`app/voice/conversation_style.py`) — HOW Mira should currently speak: language family (`ENGLISH`/`HINDI`/`HINGLISH`), script, tone. Computed by `StyleEngine.update()`, a pure function of a rolling window of the guest's own recent turns plus hysteresis (a language-family switch only commits after `MIN_TURNS_TO_SWITCH` consecutive turns clearly support it) — this replaces a single-turn, no-memory language signal that could flip on one noisy/mis-tagged utterance. `ConversationStyleProcessor` sits right after `stt`/`LanguageSyncProcessor` and writes `ConversationState.conversation_style` on every `TranscriptionFrame`. `render_style_block()` is the only place a `ConversationStyle` becomes prompt text, consumed by `StatePromptSyncProcessor`. Does **not** replace `LanguageSyncProcessor` (still drives the live TTS-language switch off Sarvam's own per-utterance tag — a different, lower-latency, audio-facing concern).
- **`ConversationQuality`** (`app/voice/conversation_quality.py`) — purely observational validator/system-health output (`ValidationResult` records). Never read by prompt-construction code, with exactly one narrow exception: `pending_style_correction` (set when `StyleComplianceMonitor` records a style-compliance `FAIL`) is read by `StatePromptSyncProcessor` to ask `ConversationStyle.render_style_block(emphasized=True)` for a more forceful rendering of the *same* style on the next turn — never a validator-authored instruction, never a different style. This is the one permitted, one-directional bridge between quality and behavior.

### `StyleComplianceMonitor` — observer, not a guard

`app/voice/style_compliance_monitor.py` replaced `response_compliance.py`'s `ResponseComplianceProcessor` entirely (removed). The old processor buffered the entire response unconditionally on every turn and, on a detected mismatch, made a second, non-streaming LLM completion call to regenerate the reply — up to several seconds of dead air on a live phone call, regardless of whether that turn ever actually violated anything. `StyleComplianceMonitor` never buffers more than a small rolling tail and **never calls an LLM**: it observes each `LLMTextFrame` as it streams past (always forwarded immediately, unconditionally) and scores the complete shadow-accumulated text once, at `LLMFullResponseEndFrame`, against the current `ConversationStyle`. On a `FAIL` it only sets `ConversationQuality.pending_style_correction = True` — no frame is ever rewritten, cut, or regenerated by this module. **There is no hidden LLM regeneration anywhere in this pipeline** — every corrective mechanism (guards, this monitor) either deterministically rewrites/truncates already-generated text or asks a later turn's prompt to try again; none of them re-invoke the LLM mid-turn.

- **STT**: `_ReconnectingSarvamSTTService` (`pipeline.py`, subclasses pipecat's `SarvamSTTService`), `mode="codemix"` — transcribes Hindi/English/Hinglish as spoken, no translation. Sarvam auto-detects the spoken language per utterance and attaches it to each `TranscriptionFrame`. The subclass exists because `SarvamSTTService.run_stt` has no reconnect-on-failure logic at all — confirmed live: Sarvam closed the STT websocket server-side mid-call (close code 1000, reason "ASR model call failed", a transient failure on Sarvam's own backend after a long guest-silent stretch), and every subsequent audio chunk immediately re-raised the same error against the now-dead socket, forever (500+ identical `ErrorFrame`s within 4 seconds in one real call) — the guest's audio was silently dropped and Mira never responded again for the rest of that call. The subclass watches for that specific error pattern and calls `_disconnect()`/`_connect()` (pipecat's own sanctioned reconnect pair — `SarvamSTTService` already calls them itself on settings/prompt changes) to recover within a ~3s cooldown-throttled retry, instead of leaving the call dead.
- **Silence watchdog** (`app/voice/silence_watchdog.py`): `SilenceWatchdogProcessor` sits right after STT so it sees every `TranscriptionFrame` plus `BotStoppedSpeakingFrame`. It nudges the guest ("Hello? Are you still there?") after each `timeout_seconds` of true silence and ends the call after the second unanswered nudge. Blank/whitespace-only transcripts (background noise, breathing) never reset its timer. `timeout_seconds=9.0` (raised from the module default of 5.0 on 2026-07-23 — confirmed live that a guest composing a Hindi dates sentence hadn't finished by 5s, their real answer landing 4s *after* the nudge fired mid-thought). Also the hang-up mechanism for a normally-ended call: the `end_call` tool arms `request_end_after_current_turn()` so the next `BotStoppedSpeakingFrame` (once the closing line finishes) ends the call. If a guest speaks again while that hangup is still pending, the watchdog cancels it and falls through to the normal flow instead. Phase 5 (`documentation/agent-conversation-improvement.md`): this processor now also owns `ConversationState.closing_state` (declared Phase 1.1) as real, prompt-visible state rather than just its own internal hangup flag — `"farewell_pending"` the moment a close is armed, `"open"` again the moment it's cancelled (guest speaks again, or `PrematureEndCallGuardProcessor`'s same-turn-question catch), `"closed"` once `EndWorkerFrame` actually fires. `StatePromptSyncProcessor` (`app/voice/state_prompt_sync.py`, sits right before the LLM) surfaces this as a direct instruction ("the call is closing, don't reopen new topics") via its existing `conversation_goal` hint mechanism (Phase 1.6) the same way it already surfaces slots/recommendations/quoted-price.
- **Redundant context guard** (`app/voice/redundant_context_guard.py`): `RedundantContextGuardProcessor` sits right before the LLM and drops a spurious re-invocation — pipecat's own deferred context-push (bundling function-call results that arrive while the bot is still speaking) can fire a second time with nothing new since the last completion. Confirmed live: this caused a call to end itself with no guest reply in between (an `LLMContextFrame` with the same message count as the one just processed gets silently dropped instead of triggering another completion).
- **Escalation phrase guard** (`app/voice/escalation_phrase_guard.py`): `EscalationPhraseGuardProcessor` sits between the LLM and TTS as a code-level backstop for the "let me loop in the host" ban in `GOLDEN_RULES` — prompting alone failed on this exact wording repeatedly across real calls. **As of 2026-07-27 it no longer tries to detect a banned phrase at all** — an earlier regex-matching version (`loop...host`/`host...loop`) kept getting bypassed by phrasing variants it didn't cover (e.g. "let me open the host," never matched by that pattern). It's inert (pass-through, zero latency) on every normal turn; the `escalate_to_host` tool call arms it (watching `FunctionCallsStartedFrame` directly, not an external `arm()` call — see the module docstring for why that raced and lost live on 2026-07-26), and it then buffers and **unconditionally replaces** the first text-bearing LLM response at/after that point with a fixed safe line ("Okay, I've noted your details -- the host will follow up with you on WhatsApp shortly to confirm.") before it reaches TTS, regardless of what the model actually said. No detection step means no phrasing variant can slip through undetected.
- **Repetition guard** (`app/voice/repetition_guard.py`): `RepetitionGuardProcessor` sits right after the LLM. Confirmed live 2026-07-27: a single Groq completion came back as 3072 completion tokens on a long, noisy call — the same clarifying question paraphrased dozens of times, some of it degenerating into a flood of ".. .. .." fragments, all spoken to the guest. Streams text through immediately by default (zero added latency on normal turns); only once it detects a near-duplicate sentence (≥60% word overlap with something already said this same turn) or a flood of very short fragments does it start silently dropping frames for the rest of that one response — the reply just ends early instead of repeating. Pairs with `max_completion_tokens=400` on the Groq LLM settings (see Groq section below), which bounds how much can be generated in the first place but doesn't by itself guarantee none of it repeats.
- **Meta-commentary guard** (`app/voice/meta_commentary_guard.py`): `MetaCommentaryGuardProcessor` drops narrator/stage-direction parentheticals like `"(Waiting for guest response)"` before they reach TTS — confirmed live 2026-07-27, a new shape of the narrator/meta-text failure `GOLDEN_RULES` already bans (see below), not literally covered by that rule's existing examples. Forwards text immediately by default; only holds text back while inside an open `(`, and drops the span if it matches known meta-commentary language (waiting/listening/pause/thinking/etc.) — legitimate parenthetical content passes through untouched.
- **Property recommendation guard** (`app/voice/property_recommendation_guard.py`): `PropertyRecommendationGuardProcessor` arms on `FunctionCallsStartedFrame` naming any property-aware tool (`recommend_properties`, `get_pricing`, `check_calendar`, `negotiate_rate`, `search_faq`, `send_photos`, `dispatch_technician`) and, for the one response right after, (1) strips any leaked `property_id` UUID from the text before TTS — confirmed live, `"(property ID 48c687d2-...)"` was spoken verbatim — and (2) for `recommend_properties` specifically, checks whether the reply actually names one of the returned properties; if not, overrides the reply entirely with a guaranteed-correct line built straight from the tool's own real result. `recommend_properties`'s own result string (`handle_recommend_properties` in `tool_handlers.py`) is fed to the guard directly from `app/voice/tools.py`'s wrapper, synchronously before `result_callback` — not racy the way an external `arm()` call would be, since the completion the guard needs to check is *caused* by that same callback. Phase 4b (`documentation/agent-conversation-improvement.md`), "Tool Output Fidelity": the identical pattern generalized to every other property-aware tool, since the model is free to reinterpret any tool's structured result before speaking it, not just recommend_properties'. `get_pricing`/`negotiate_rate` each gained an `on_priced` callback (handed the real `Property`/`PriceBreakdown`/`NegotiationResult`) so the guard can verify the reply states the same total it actually computed; `check_calendar` gained `on_checked` (a real availability bool) so the guard can catch a flat "available"/"not available" contradiction; `recommend_properties` also gets a capacity-fidelity check reusing the same recorded options (a named property's stated guest-count must match its real `max_guests`); `search_faq` gained `on_answered` (the resolved property's real `amenities`) so the guard can catch the reply naming a specific amenity keyword that was never actually on file (via the same fixed synonym map `app/services/amenity_taxonomy.py` already uses for facet filtering).
- **Premature end-call guard** (`app/voice/premature_end_call_guard.py`): `PrematureEndCallGuardProcessor` sits right before TTS. Confirmed live 2026-07-26: one completion both asked a real question ("Anything else you'd like to sort out?") and called `end_call` in the same turn, hanging up before the guest could answer. Watches for a same-turn `end_call` + a `"?"` anywhere in that turn's text; if both are present, calls `silence_watchdog.cancel_end_request()` so the call falls through to the normal silence-nudge path instead of ending the instant that line finishes playing. Never rewrites the text itself — the question still gets asked normally.
- **Style compliance monitor** (`app/voice/style_compliance_monitor.py`): `StyleComplianceMonitor` sits after `MetaCommentaryGuardProcessor` (scoring the model's own original wording, not a guard-substituted safe line) and before the tool-fidelity guards. Streaming observer, not a guard — see "Conversation architecture" above. Never buffers more than a small rolling tail, never calls an LLM, never rewrites/cuts a frame; on a detected language/style mismatch it only flags `ConversationQuality.pending_style_correction` for the next turn's prompt to react to.
- **Response shape guard** (`app/voice/response_shape_guard.py`): `ResponseShapeValidatorProcessor` sits LAST, immediately before `EndCallReliabilityGuardProcessor`/TTS — after every rewrite above has already run. Phase 4.3 (`documentation/agent-conversation-improvement.md`). Confirmed live 2026-07-31 (catalogue item C3): a single completion concatenated three separate questions with no guest turn in between (one with literally no space after the `?`) — low word overlap by construction, so `RepetitionGuardProcessor`'s sentence-similarity check structurally cannot see this shape, since it targets a sentence repeating *itself*, not several different sentences glued together. **Streaming, not buffering** (response output architecture redesign — see above): forwards each completed sentence immediately, re-checking five of its six violation types incrementally as text accumulates; the sixth (`ends_mid_clause`) is only meaningful against the complete response and is checked once, at `LLMFullResponseEndFrame`. Checks are deterministic/mechanical only (never a second LLM judgment): more than one unconnected question, more than one greeting opener, a duplicated escalation safe-line, a duplicated-punctuation flood (e.g. `".. .. .. .."`, catalogue item H2's shape), more than one recommendation-block intro, or a response that ends mid-clause. On any violation, stops forwarding further sentences for the rest of that response — the violating sentence is never the first one in any real case this guard exists to catch, so this reproduces "keep only the first clean sentence" as an emergent effect of streaming rather than post-hoc trimming.
- **End-call reliability guard** (`app/voice/end_call_reliability_guard.py`): `EndCallReliabilityGuardProcessor` sits last, immediately before TTS. Guarantees `end_call` actually fires whenever the model speaks `DEFAULT_CLOSING_PHRASE` — confirmed live: a guest-initiated ("thank you") close sometimes produced the closing line as plain text with no paired `end_call` tool call, leaving the call open indefinitely.
- **Language sync** (`app/voice/language_sync.py`): `LanguageSyncProcessor` watches that detected language and, on a change, pushes a `TTSUpdateSettingsFrame` (delta-only, so voice/model/pace are untouched) that Sarvam TTS applies live to its websocket — so a guest who switches to Hindi/Hinglish mid-call gets a Hindi TTS voice instead of always being answered in English. The LLM already mirrors the guest's language in its reply text (`GOLDEN_RULES` in `system_prompt.py`); this is what makes the *audio* match too.
- **LLM**: built by `_build_llm()` — see Groq fallback section below. Function-calling into the 12 tools in `app/voice/tools.py`.
- **TTS**: `SarvamTTSService`, `pace=1.15` (slightly faster than the 1.0 default, tuned for phone-call cadence), starting `language=Language.EN_IN` and switched to `Language.HI_IN` at runtime by `LanguageSyncProcessor`.
- **Turn strategy**: `SpeechTimeoutUserTurnStopStrategy(user_speech_timeout=0.9)` by default, or `HybridCompletenessUserTurnStopStrategy` if `TURN_DETECTION_STRATEGY=hybrid_experimental` — see Turn detection below. Deliberately not pipecat's default `LocalSmartTurnAnalyzerV3` (local ONNX inference), which competes for CPU with the real-time audio loop on a dev box.
- **VAD**: `create_vad_analyzer(VADParams(confidence=0.85, min_volume=0.7, start_secs=0.35))` (`app/voice/vad.py`) — `confidence`/`min_volume` raised from pipecat defaults (0.7/0.6) so background noise or a second nearby voice doesn't trigger a false interruption that cuts off in-progress TTS (~1.3s dead air per Sarvam TTS reconnect, confirmed via call logs). `start_secs` raised from pipecat's 0.2s default to 0.35s on 2026-07-23 after guest feedback that the bot cut them off too readily — 0.2s fires an interruption after only a fifth of a second of sound (closer to a mic bump than speech). The exact 0.35s value was chosen as plausible and still needs live-call confirmation that it doesn't make genuine interruptions feel sluggish. `create_vad_analyzer` exists because `SileroVADAnalyzer.__init__` synchronously builds an `onnxruntime.InferenceSession` from the packaged model file — ~2s, confirmed via call logs, and `_run_pipeline` builds a fresh analyzer per call (its VAD state can't be shared across concurrent calls). `app/voice/vad.py` loads that session once at process/import startup and hands each call a lightweight analyzer wrapping the shared, already-compiled session — only the per-call state arrays are fresh, the expensive part isn't repeated.
- **Metrics**: `PipelineParams(enable_metrics=True, enable_usage_metrics=True)` — per-stage TTFB and exact prompt/completion token counts logged per call, the basis for real $ cost tracking.

### `pipecat-ai` version pin

`requirements.txt` pins `pipecat-ai[websocket,webrtc,anthropic,groq,sarvam]>=1.5.0,<2.0` (previously unbounded `>=0.0.60`). Found live: Railway had silently rebuilt onto 1.5.0 on a fresh deploy while local dev was still testing against 1.4.0 installed weeks earlier — an unpinned range means every fresh `pip install` (every deploy) can land on a different release than whatever was last actually tested, with no record of which version any given deploy is running. Bump the floor deliberately when there's a real reason to upgrade.

### Call-connect-to-greeting latency

Real Exotel call logs (2026-07-21) broke the delay down into three pieces, in order: (1) our own DB setup (guest/session/property resolution, ~1.7s even with the DB warm — see `_check_db_health` in [architecture.md](architecture.md)), (2) STT then TTS connecting to Sarvam **sequentially**, ~1.0-1.3s each (~2.3s combined) because pipecat's own `StartFrame`-driven pipeline startup connects each stage in pipeline order, and (3) TTS's own synthesis time (~0.5-0.7s TTFB/TTFA).

**Attempted and reverted**: pre-connecting STT and TTS concurrently via `asyncio.gather(stt._connect(), tts._connect())` right after constructing them, before the `Pipeline` object exists. This broke every real call in production (`Exception: SarvamTTSService#0: TaskManager is not initialized`) — pipecat only assigns a service's `task_manager` once it's attached to a running `Pipeline`/`PipelineWorker`, which happens *after* construction, so any `self.create_task(...)` call inside `_connect()` (both STT and TTS spawn a receive-task) has nothing to attach to yet. Reverted same-session. A real fix would need to hook in *after* `task_manager` assignment but *before* `StartFrame` propagation reaches STT/TTS — pipecat's `WorkerRunner._setup()` (which assigns `task_manager`) and `_wait_for_pipeline_start()` (which triggers `StartFrame`) run back-to-back internally with no exposed gap for application code to use, so this isn't a small change — it would mean replicating part of pipecat's own private startup sequence. Deprioritized (2026-07-21) as not worth the risk for the ~1s it would save, especially having just caused one outage attempting it. If revisited, test against a real call locally first, not just reasoning from the pipecat source.

### Bot speaks first

The greeting (`first_message`) is fixed and host-authored (`User.agent_first_message`, templated via `_resolve_template` with `{host_name}`/`{property_name}`/`{city}`/`{guest_name}` placeholders — any placeholder that doesn't apply resolves to `""`). It is pre-seeded into the LLM context as an assistant turn (so the model knows it was already said — the "don't repeat greeting" rule in `GOLDEN_RULES` depends on this), and spoken via `worker.queue_frame(TTSSpeakFrame(first_message))` on the transport's `on_client_connected` event, guarded by a one-shot `greeting_sent` flag (the event can fire more than once per connection). `queue_frame` injects at the pipeline source so it flows through every real stage; pushing directly into `llm`/`tts`, or letting the LLM generate the opening line live, both failed in testing (garbled/hallucinated output, or skipped synthesis).

**Known unresolved issue**: the double-greeting guard stops the same event handler firing twice within one `_run_pipeline` call, but a double greeting was still observed live via the browser test page even with the guard active and confirmed deployed. Root cause not yet found — most likely two genuinely separate `/test/offer` POSTs (two full pipeline runs, each correctly greeting once) rather than one handler firing twice, but this wasn't confirmed against Exotel phone calls specifically. Check `/tmp/*.log` or the live backend's own stdout for two `POST .../test/offer` or `WebSocket ... [accepted]` lines close together before assuming the guard itself is broken.

### Connect-to-greeting gap / ringing tone (Exotel calls only)

Even with VAD preloaded (see above) and no double greeting, a real Exotel call still has ~4-6s of unavoidable setup between the websocket accepting and Mira's first word — sequential DB lookups in `run_voice_pipeline`, then `_run_pipeline`'s own build (LLM/TTS construction, tool wiring) followed by Sarvam STT and TTS websocket handshakes (each ~1s, sequential — TTS's `start()` can't run until STT's has propagated the `StartFrame` downstream, since STT sits upstream of TTS in the pipeline; not cleanly fixable without patching pipecat's own frame-propagation internals). A pre-recorded *spoken* holding message was tried here first ("Welcome to Mira AI. Connecting you now.") and was later removed.

It's since been replaced with `app/voice/ringing_audio.py`'s `play_ringing_tone` — a synthesized ringback tone (`app/voice/assets/ringing_tone_8000.wav`, generated once offline via `scripts/generate_ringing_tone.py`: pure sine synthesis, no TTS/API call, one 4s ring cycle — 1s of 400Hz tone + 3s silence) looped and written directly onto the raw Exotel websocket, same wire shape as `ExotelFrameSerializer.serialize`'s `{"event": "media", "streamSid": ..., "media": {"payload": <base64 PCM>}}`, chunked into 20ms/320-byte frames. Bypasses pipecat entirely, same reason as the old holding message: there's no pipeline/transport yet at this point to push a frame into.

Unlike the old fixed-length clip, this loops indefinitely — there's no "natural end" to wait for, so **the only thing that ever stops it is cancellation**, not the clip finishing. That's what makes the stop airtight rather than approximate: `run_voice_pipeline` starts the task (`asyncio.create_task`) at the very top, right after `call_data.stream_id` is known, then threads it through `_run_pipeline`/`_run_pipeline_inner` as `ringing_audio_task`. It's cancelled and *awaited* in three places, all before the real transport can start writing to the same socket:
- The early-return branch in `run_voice_pipeline` (no `Property`/lead line configured for the dialed number).
- Immediately before `runner.run()` inside `_run_pipeline_inner` — the last safe moment, since that call is what triggers the transport's own `StartFrame`-driven `start()` and its first real audio write to the same socket. Cancelling any earlier would waste coverage; any later would race two writers on one websocket.
- A `finally` block wrapping the inner call in `_run_pipeline`, so a build-time exception (e.g. `SarvamTTSService`/`_build_llm` failing) can't leave the task orphaned, still looping against a socket nothing else is managing.

Because `task.cancel()` followed by `await task` only returns once the ringing coroutine has actually unwound (asyncio never runs two coroutines' code concurrently on one event loop thread), there is no interleaving window where both the ring tone and Mira's real audio could be writing to the socket at once — the guarantee comes from *where* cancellation happens relative to `runner.run()`, not from any timing assumption. Tests: `tests/test_ringing_audio.py` (loops past one cycle; cancel+await stops sends immediately with no further frames arriving after; malformed/failing sends are swallowed, not raised) and `tests/test_run_voice_pipeline_ringing.py` (the early-return path actually stops the task against a real unmatched dialed number, no DB mocking).

Browser-test calls (`run_browser_voice_pipeline`/`run_browser_lead_pipeline`) don't get this — there's no raw socket to write Exotel-shaped JSON frames onto over WebRTC, and their setup path is shorter to begin with (no `get_active_booking`/host-by-phone DB lookup).

## Busy Call Recovery

A second simultaneous call to a host/property already on a live call is rejected as "busy" rather than starting a second competing pipeline, and the rejected guest is automatically re-engaged over WhatsApp instead of just hearing a busy tone and hanging up. Built across several deliberately separated components (see `app/services/call_coordinator.py`'s own docstring for the full accept/reject design):

- **`CallCoordinator`** (`app/services/call_coordinator.py`) is the single authority on "does this host/property already have a live call?" — nothing else. `acquire_or_reject`, wired into both `run_voice_pipeline` (Exotel) and `run_voice_pipeline_twilio` immediately after host/property resolution, returns exactly `Decision.START_PIPELINE` or `Decision.BUSY_RECOVERY` — the pipeline never sees anything beyond the `Lease` dataclass (`token`/`holder_ref`/`expires_at`). **Redis-backed, not Postgres**: ownership is a single Redis key, `call_lease:{host_user_id}:{property_id}` (`NIL_PROPERTY_ID` sentinel for Lead Agent calls, same convention the old Postgres design used), holding a small JSON value whose `token` field is the actual ownership/fencing credential — see `app/integrations/redis_lease_client.py`. `acquire()` is one atomic `SET key value NX EX 45`; `renew()`/`release()`/`transfer()` are each one atomic Lua script that verifies the caller's token still matches the currently-stored lease before mutating anything, so a stale/delayed caller (e.g. a renewal arriving after its own lease already expired and was re-acquired by a different caller) can never touch a lease it no longer owns. Redis TTL is the entire expiry mechanism — no lazy Postgres-style "is this row still active" check, no sweep job. `app/models/call_lease.py` (the pre-migration Postgres table) still exists in the repo but is written to by nothing — see that file's own docstring for the staged-removal plan.
- **Lease renewal**: `DEFAULT_LEASE_TTL` is 45s. `_run_pipeline` (`app/voice/pipeline.py`) starts a background `_renew_call_lease_periodically` task alongside the real pipeline (renewing roughly every 20s, `_LEASE_RENEWAL_INTERVAL_SECONDS`) so a lease survives for the full duration of a live call, not just its first 45 seconds — cancelled in the same `finally` block that already releases the lease on every exit path (normal end, construction failure, cancellation). Fails open: a renewal error (Redis outage, or a genuinely lost lease) is logged and the loop simply stops rather than raising into the live call.
- **Redis outage behavior**: `acquire_or_reject` fails open to `START_PIPELINE` (a live guest call must never be rejected solely because Redis is down) but logs loudly (`lease_redis_unavailable`) as an explicit, alertable signal that busy-call protection is degraded — not a silent fallback. `renew`/`release` always fail open silently (never allowed to terminate or endanger an in-progress call); see `app/services/call_coordinator.py`'s module docstring for the full reasoning.
- **On `BUSY_RECOVERY`**: the pipeline plays a short placeholder clip (`app/voice/ringing_audio.py`'s `play_busy_message`, reusing the same raw-websocket PCM-streaming primitive the ringing tone above uses) and hangs up — no pipeline is ever constructed for the rejected call. `RecoveryService.handle_busy_recovery` (`app/services/recovery_service.py`) is then fired detached (`asyncio.create_task`, strictly after the DB session used for the accept/reject decision has closed) to turn the rejection into something the host can follow up on: it finds/creates a `GuestProfile`, creates or reuses an open `Lead` (`recovery_reason="BUSY_CALL"` — see [database.md](database.md)'s `leads` table; a repeat busy-rejected caller lands on the same `Lead`, not a new row per attempt), creates a `Notification` (`channel="busy_recovery"`), and sends WhatsApp to both sides: the guest gets a single short message ("Mira is helping another guest, please call back in about 5 minutes" — matching what they're already told out loud on the call, `BUSY_MESSAGE_TEXT` in `app/voice/ringing_audio.py`; `scripts/create_busy_recovery_template.py`'s Content Template, falling back to plain text if unconfigured), and the host gets the same `mira_escalation` template `escalate_to_host` uses (see below) with the guest's name (when on file, `GuestProfile.name`) and number.
- There is no inbound WhatsApp reply handling. An earlier version of the guest-facing message was an interactive numbered menu (Property/Pricing/FAQs/Photos/Talk-to-host/Something-else) with a whole reply-parsing subsystem behind it (`app/services/whatsapp_reply_service.py`, `POST /webhooks/whatsapp/inbound`) — removed in favor of the single "call back in 5 minutes" message above, since the whole premise is that Mira frees up again within minutes rather than needing a text-based self-service channel. `GET /analytics/recovery`'s `recovered`/`avg_recovery_time_seconds` fields are consequently historical-only (frozen at whatever pre-cutover data exists) — see `app/api/v1/analytics.py`'s own comment.
- **Recovery Analytics** (`GET /analytics/recovery`, `app/api/v1/analytics.py`) reads Busy Calls/Converted/Lost counts and average host-response time directly from the `Notification`/`Lead` rows RecoveryService already writes — see [api.md](api.md) for the exact query semantics (why `Notification`, not `Lead`, is the source of truth for attempt counts).

### Silence watchdog and call-ending tools

`SilenceWatchdogProcessor` (`app/voice/silence_watchdog.py`) sits in the pipeline directly after `stt` (see the stage list above — the diagram omits it for brevity but it runs between `SarvamSTTService` and `LanguageSyncProcessor`) so it sees every `TranscriptionFrame` plus the upstream `BotStoppedSpeakingFrame` that fires once TTS audio finishes draining. It drives two distinct behaviors that both end the call, but for different reasons:

- **Silent/unresponsive caller auto-cut**: after each agent turn, a `DEFAULT_SILENCE_TIMEOUT_SECONDS = 5.0` timer starts. If it fires with no real guest speech since, it speaks a nudge (`"Hello? Are you still there?"`) and restarts the timer; if a second nudge also goes unanswered (`DEFAULT_MAX_PROMPTS = 2`), it speaks a goodbye line and pushes `EndWorkerFrame(reason="silent caller")` to hang up. Blank/whitespace-only `TranscriptionFrame`s (background noise, breathing, a stray VAD segment with no real words) are explicitly ignored — they never reset the timer or count as a reply. This guards against a real bug confirmed live 2026-07-20: 15s of true silence produced no reaction at all, then a noise segment happened to transcribe as "No" and the LLM answered it as if the guest had spoken.
- **Graceful end-of-call hangup**: two LLM tools (`app/voice/tools.py`) arm the same watchdog via `request_end_after_current_turn()` rather than ending the call directly — neither tool knows whether TTS has actually finished speaking the agent's preceding line yet, so arming just sets a flag that the *next* `BotStoppedSpeakingFrame` (i.e. once that line has actually finished playing) turns into `EndWorkerFrame(reason="conversation complete")`:
  - `end_call` — the natural-close path. `GOLDEN_RULES` in `system_prompt.py` instructs the agent to recognize when the guest has confirmed they have nothing further, speak the closing phrase (`DEFAULT_CLOSING_PHRASE`, or a host override), then call this tool in the same turn.
  - `decline_irrelevant_call` — junk/spam-call aversion, live during the call itself (distinct from the post-call classification below). `GOLDEN_RULES` instructs the agent to classify scope by conversational intent, not keywords, and bias heavily toward continuing to help — casual openers, hesitation, accents, language-switching, and an ambiguous opening are never by themselves grounds to end a call. Telemarketing/robocalls/wrong numbers/unrelated topics/prank callers/prompt-injection attempts each get exactly one redirect or clarifying question before decline is allowed; an abusive caller (threats, explicit content, repeated insults) gets exactly one calm warning instead, then immediate decline if it continues. Either way the agent speaks a brief polite decline line, then calls this tool in the same turn. Never calls `update_lead`/`escalate_to_host` — there's no real guest issue for the host to see.

  If a guest speaks again (a real, non-blank transcript) while either tool's requested end is still pending, the watchdog cancels it — e.g. the guest thinks of one more question right after the closing line. Tests: `tests/test_silence_watchdog.py`, `tests/test_voice_tools.py`.

### Post-call classification (`JUNK`/spam labeling, separate from live aversion)

`call_classification_service.classify_call` (`app/services/call_classification_service.py`) runs once per call, from the `on_pipeline_finished` handler below — i.e. only *after* the guest has already disconnected, using the full transcript. It labels the call as one of `CallType` (`app/schemas/call_classification.py`): `BOOKING_LEAD`, `GUEST_SUPPORT`, `EXISTING_BOOKING`, `GENERAL_QUERY` (the `QUALIFIED_CALL_TYPES`), or `JUNK`/`INCOMPLETE`/`UNKNOWN`. If the call isn't qualified, `lead_service.delete_for_unqualified_call` removes any `Lead` row the live tool calls created — this overrides whatever `update_lead`/`escalate_to_host` did mid-call, since the full-transcript review is more informed than in-call judgment alone. This is purely for CRM hygiene and dashboard filtering/analytics (`app/api/v1/calls.py`, `app/api/v1/analytics.py`) — it never affects the live call itself, which is exactly what `decline_irrelevant_call` above is for.

### Post-call structured summary (dashboard "AI summary" card)

`call_summary_service.summarize_call` (`app/services/call_summary_service.py`) runs alongside the classification call above, from the same `on_pipeline_finished` handler, over the same transcript. It produces a structured `CallSummary` (`app/schemas/call_summary.py`: booking snapshot, 3-5 sentence conversation summary, outcome + reason, host actions, key details, missing information) persisted via `call_service.set_call_summary` into `CallSession.ai_summary` (JSONB). Same one-shot-LLM-after-the-call-ends shape as classification — not built on `_build_llm()`/pipecat, never raises (degrades to a safe fallback summary on any failure), same provider fallback chain (Groq → Anthropic → OpenRouter). Rendered by the dashboard's Call Details page (`frontend/src/app/dashboard/calls/[id]/page.tsx`) instead of a plain paragraph.

### Call teardown

`on_pipeline_finished` assembles the transcript from `context.messages` and calls `call_service.finalize_call_session`, then runs the post-call classification and summary generation above, then backfills the caller's phone/property onto the `Lead` (`lead_service.backfill_lead`, fills only blank fields, never creates a lead) or deletes a near-empty lead (`lead_service.delete_if_empty`). `on_client_disconnected` calls `worker.cancel()` — without this, a call ending by the browser tab closing (rather than an explicit disconnect click) never reaches `on_pipeline_finished`, leaving the call stuck at `status="in_progress"` forever.

## Tools (`app/voice/tools.py` → `app/services/tool_handlers.py`)

Each tool is a pipecat "direct function" — name/description/parameter schema are extracted from type hints + docstring, no separate JSON schema to maintain. `call_session_id`/`property_id`/`host_user_id`/`conversation_state` are bound via the `build_voice_tools()` factory closure, not passed by the LLM.

| Tool | Purpose | Handler |
|---|---|---|
| `check_calendar` | Check property availability for given dates; also locks the property in Lead Agent calls. | `handle_check_calendar` |
| `get_pricing` | Quote total price. If `Property.exact_airbnb_pricing` is set, fetches this exact listing's live price for the exact requested dates from SearchApi.io instead of computing base+surge+fee+tax; falls back to that math if the live fetch fails. Must be called first with `apply_discounts=false`; only re-called with `apply_discounts=true` after guest pushback. | `handle_get_pricing` (→ `pricing_engine.calculate_price`, see [research-flow.md](research-flow.md)) |
| `dispatch_technician` | Notify a technician for a physical issue (plumbing/electrical/ac/wifi/lock/general); falls back to a host notification if none on file. | `handle_dispatch_technician` |
| `send_whatsapp` | Send a guest/host-facing WhatsApp message (real send via Twilio Sandbox — see below; also logged to `Notification`). | `handle_send_whatsapp` |
| `send_photos` | Send the guest a link to a property's photo gallery (one link, not individual images) over WhatsApp + a host-inbox email fallback. | `handle_send_photos` |
| `escalate_to_host` | Escalate to the host (in-app notification + fire-and-forget email); also upserts whatever lead data it already has. | `handle_escalate_to_host` |

As of 2026-07-27, a recognized region query matches **only** against that expanded locality list, never the literal region phrase against `neighborhood_info` free text — confirmed live that a North Goa (Siolim) property's `neighborhood_info` mentioning "Dabolim (South Goa airport)" as a travel-time reference was wrongly matching a "South Goa" query on the raw-phrase substring match this replaced. Result string is a numbered, newline-separated list (not `" | "`-joined) since real imported property names routinely contain a literal `\|` themselves — confirmed live that the old joined format tore names apart at every internal `\|`, reading a shared brand suffix ("Pause Project") back as if it were the property name. If no single property fits the requested guest count, falls back to returning smaller units (same location/budget filters, guest-count cutoff dropped) and tells the model to suggest booking two of them together, instead of a flat "nothing found" — hosts with several small units at one property routinely accommodate larger groups this way. | `handle_recommend_properties` |

Logs a gap (`UnansweredQuestion`) only if the property itself is unknown — see the "Known gap" note in [database.md](database.md#unanswered_questions-unansweredquestion-appmodelsunanswered_questionpy). | `handle_search_faq` |

Silent — never touches `Lead`. | none (see Silence watchdog section below) |

All handlers return a natural-language string — this is fed back to the LLM as the tool result and is often read back near-verbatim to the guest, so results are phrased for speech, not JSON. `ValidationError` on tool args is caught in `app/voice/tools.py` and returns a fixed re-ask string (`INVALID_ARGS_MESSAGE`) instead of erroring the turn.

### Host/guest notifications (in-app + email + Twilio WhatsApp sandbox)

`escalate_to_host`/`send_whatsapp`/`send_photos` all write to the `Notification` table (`app/services/notification_service.py`), which is what the dashboard's Live Requests feed polls/streams — this is a record of what was sent, not the delivery mechanism itself.

Real WhatsApp delivery goes through Twilio's Sandbox (`app/integrations/twilio_client.py`, `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_WHATSAPP_FROM`), not a Meta-approved WhatsApp Business number — Exotel's WhatsApp Business API requires Facebook Business Manager ID + Exotel KYC/Meta approval before any sending number exists, so Twilio's instant shared sandbox number stands in for now. The sandbox has **two** real constraints, confirmed live as genuinely distinct failure modes:
1. It can only message numbers that have first texted "join `<code>`" to the sandbox number from WhatsApp — fine for testing against the host's own phone, not usable for arbitrary real guests until upgraded to a real WhatsApp Business number.
2. Even an already-joined number only stays reachable for **24 hours from their last inbound message** to the sandbox — WhatsApp's customer-service-window policy, not a Twilio-specific limit. After that window closes, freeform text sends fail with Twilio error `63016` ("outside the allowed window ... use a Message Template") — confirmed live via the Twilio API directly (`GET /Messages.json` showed `status: "undelivered", error_code: 63016` for two `send_photos` sends, while sends to the same number the *previous* day showed `status: "delivered"`). `send_photos`/`send_whatsapp` have no template fallback for this (unlike `escalate_to_host`, see below) — the guest/host has to re-message the sandbox number to reopen the window. Real fix (not yet built) is a pre-approved WhatsApp template for photo/general sends, same pattern as the escalation template.

`TWILIO_*` unset = falls back to the in-app notification only, same pattern as every other optional integration here.

`escalate_to_host` also WhatsApps the host directly (`User.phone`, separate from the guest-facing sandbox constraint above — the host is the one who joins the sandbox for this). Uses a `twilio/call-to-action` Content Template (`TWILIO_ESCALATION_TEMPLATE_SID`, created once via `scripts/create_escalation_template.py`) so the message renders a real "Go to Dashboard" **button** instead of a raw URL — WhatsApp auto-linkifies (and generates an ugly link-preview card for) any bare URL in plain text, and there's no per-message API flag to suppress that; a Content Template button is the only way around it. Falls back to a plain-text message (with a bare URL) if `TWILIO_ESCALATION_TEMPLATE_SID` isn't set. Message body uses an emoji keyed off urgency (`_URGENCY_EMOJI` in `tool_handlers.py`) plus bold labeled fields (`*Property:*`, `*Issue:*`, etc.) — plain prose was found to be unreadable when a host has several escalations stacked in one WhatsApp thread.

`handle_escalate_to_host` and `handle_send_photos` additionally fire an email (`app/integrations/email_client.py`, plain SMTP, any provider) via `asyncio.create_task` — not awaited, so a slow/misconfigured SMTP server never adds latency to the live tool call. `SMTP_*` unset = skipped silently, same pattern as `BRIGHT_DATA_API_KEY`. `send_whatsapp` itself has no email fallback — that hook is specific to `escalate_to_host`'s host-facing summary and `send_photos`'s gallery link.

**⚠️ Currently broken in production, confirmed live (2026-07-21)**: Railway's Trial-tier network policy blocks outbound SMTP (port 587) — every email send times out (`aiosmtplib.errors.SMTPConnectTimeoutError: Timed out connecting to smtp.gmail.com on port 587`), silently, since the send is detached and never awaited. `SMTP_*` being correctly configured doesn't help; the port itself is blocked at the platform level. Real fix is switching `email_client.py` from raw SMTP to an HTTP-based email API (Resend, SendGrid, Postmark, etc.) — not yet built. See [architecture.md](architecture.md)'s Railway section.

## GOLDEN_RULES (`app/prompts/system_prompt.py`)

A fixed block of prompt rules injected into both `GUEST_SUPPORT_INSTRUCTIONS` and `LEAD_AGENT_INSTRUCTIONS`, layered underneath host customization (`agent_persona`, `agent_first_message`, `agent_escalation_phrase`) so a host can personalize tone without disabling a safety rail. Key constraints:

- **Never invent tool call arguments**: applies the "never hallucinate" rule just as strictly to `check_calendar`/`get_pricing`/`negotiate_rate`'s arguments as to what's said out loud — never call these with a check-in/check-out date or guest count the guest hasn't actually stated; ask for a missing value and wait for the real answer instead of inventing a plausible-sounding placeholder. Confirmed live (2026-07-21): Mira called `check_calendar` with a check-in/check-out/guest-count the guest never gave, then told them the property was "available" for those invented dates.
- **No narrator/meta text**: extends the existing "no turn labels" rule to also catch stage-direction/wrap-up phrases that aren't turn labels but are just as out of place on a phone call — "This is the end.", "To summarize,", "End of call." Confirmed live: `"---This is the end.---"` got spoken directly to a guest, appended after a real sentence. A further variant, `"(Waiting for guest response)"`, recurred live 2026-07-27 in a shape this rule's own examples didn't literally cover — that one is **additionally enforced in code** by `MetaCommentaryGuardProcessor` (see Pipeline stages), same reasoning as the escalation-phrase backstop below: this class of failure hasn't reliably stayed fixed on prompt wording alone.
- **Mid-call "hello" never repeats the last answer**, not just the greeting — a guest saying "hello" partway through is checking the line is live, not asking to hear the last answer again. Confirmed live: a guest said "Hello" mid-call and got a near-verbatim repeat of a full attractions answer instead of a brief "I'm here."
- **Re-ask rule also covers the guest's immediately preceding message**, not just earlier ones — confirmed live: a guest said "My name is Khushi" and the very next reply opened with "Great, could you tell me your name, please?", re-asking the exact thing just given one turn ago. If a reply is about to open with an acknowledgement ("Great,", "Got it,"), that's itself a signal the info is already in hand.
- **Pricing order**: always quote `get_pricing(apply_discounts=false)` first; only call again with `apply_discounts=true` (or `negotiate_rate` if the guest names an offer) after the guest pushes back. Never volunteer a discount unprompted.
- **Competitor comparisons**: if the guest compares price to Booking.com/MMT/Agoda or asks for a discount in English/Hindi/Hinglish, never invent a match — route through the pricing-order rule above.
- **Occasion handling**: record exactly what the guest said about a birthday/anniversary/honeymoon/etc. via `update_lead`'s `occasion`/`conversation_summary` fields; never invent host-facing suggestions ("consider offering a cake" is explicitly banned).
- **Escalation-after-verbal-accept**: the moment a guest verbally accepts a price and wants to proceed, that's a booking request requiring host approval — there is no tool that finalizes a booking. The prompt requires an immediate `update_lead(lead_temperature="hot", ...)` followed by `escalate_to_host`; a verbal "I'll lock that in" with no backend calls behind it means the host never finds out (step 7 of the Lead Agent workflow).
- **Voice-specific formatting**: no markdown, one question per response, one response per turn (never simulate the guest's side or write any turn label like `"Guest:"`/`"User says"`/`"User:"` in any position — a real, confirmed live-call failure mode, not hypothetical), concise (1-2 sentences unless reciting a requested list), never repeat the greeting or any prior sentence verbatim, no filler on interruption.
- **Dates**: resolved via a pre-computed "today anchor" (`_today_anchor()`) rather than trusting the LLM's own weekday arithmetic. `"This weekend"` and `"next weekend"` are two genuinely different weekends (not the same dates — a real bug this session), and a resolved date is always spoken back naturally ("18th of July"), never as raw `YYYY-MM-DD`.
- **Don't re-ask known info**: if the guest already gave their name/phone earlier in the same call, use it — never ask again or act like it's unknown.
- **FAQ-first**: any property/support question must go through `search_faq`. It may return a verified FAQ answer or the property's full on-file details (see the `search_faq` tool row above) — either way, only answer with what's actually in what it returned; if the specific thing asked isn't actually present, that still counts as "no verified information": say so and escalate, never answer from memory/guesswork or loosely infer from unrelated details in the result.
- **Filler-only turns don't trigger a re-ask** (added 2026-07-23): a guest turn that's just a thinking sound ("Hmm", "um", "uh", "haan") with no real answer is not a cue to restate the last question — stay quiet or say "Take your time." Confirmed live: "how many guests?" got re-asked in different wording 4s after a guest said "Hmm" while still composing their answer.
- **Speak tool results before reacting to them** (added 2026-07-23): after `recommend_properties`/`search_faq`/`check_calendar`/`get_pricing` etc., the very next thing said must include the actual returned content (property names, the answer, the price) — never jump to a follow-up reaction that assumes the guest already heard something not yet spoken. Confirmed live, recurring as recently as 2026-07-27: `recommend_properties` returned real results and the next line skipped straight to a follow-up reaction without ever naming a property — a genuine, repeated prompt-compliance gap, which is why `recommend_properties` specifically now has a code-level guarantee too: `PropertyRecommendationGuardProcessor` (see Pipeline stages) overrides the reply with a guaranteed-correct line built from the tool's own real result if none of the returned property names actually got said.
- **"Loop in the host" ban** — never say "let me loop in the host" or any variant, for any escalation reason; say a concrete next step + channel instead ("the host will follow up on WhatsApp shortly"). This has recurred on real calls repeatedly despite the rule — including phrasing variants ("let me open the host") a regex-based code backstop still missed — so as of 2026-07-27 the reply after `escalate_to_host` is **unconditionally replaced** in code by `EscalationPhraseGuardProcessor` (see Pipeline stages), regardless of what the model says. The prompt rule is no longer load-bearing for this specific phrase — the processor is.
- **Never quote ₹0 as a price** — enforced in code, not just prompt: `handle_get_pricing`/`handle_negotiate_rate` return a "no confirmed rate, escalate" directive instead of any non-positive total (confirmed live: a `base_price=0` property was quoted as "zero rupees for the night"). See the pricing section in [research-flow.md](research-flow.md).

## Groq multi-model fallback

Config: `GROQ_MODEL` (`openai/gpt-oss-120b`, the configured default/first choice) and `GROQ_MODELS` (JSON array string, default `["openai/gpt-oss-120b", "llama-3.1-8b-instant", "openai/gpt-oss-20b"]`) — the fallback chain `_build_llm()` actually walks.

- **Health checks**: `_check_llm_health` in `app/main.py` runs every 60s (plus once at startup), pinging each Groq model with a 1-token request. Success/failure (with latency) is stored in the module-level `llm_health` dict. This does double duty: keeps the route warm (avoids cold-start latency) and marks a model down on a 429 (a per-model rate-limit cap — the account is on a **paid** Groq plan as of 2026-07-07, so limits are much higher than free tier but not unlimited, especially under bursty call load).
- **Model selection**: `_pick_groq_model()` in `pipeline.py` returns the first model in `settings.groq_models` not marked down in `llm_health` (falls back to the first model if health data isn't populated yet, e.g. cold start).
- **Live 429 handling**: `_FallbackGroqLLMService` (subclass of pipecat's `GroqLLMService`) overrides `create_client` to set `max_retries=0` on the underlying `AsyncOpenAI` client (otherwise the SDK's own default retry/backoff would blindly re-hit the same rate-limited model before this fallback gets a chance) and overrides `get_chat_completions` to retry the *next* model in `settings.groq_models` immediately, in the same call turn, on a `RateLimitError` — rather than waiting for the next 60s health-check pass. It starts from whichever model `_build_llm` already picked, not always `groq_models[0]`.
- **`reasoning_effort: "low"`**: applied only when `"gpt-oss" in model` (other models like `llama-3.1-8b-instant` 400 on this param). Disables gpt-oss's hidden chain-of-thought pass — a real source of multi-second latency on a live call. Applied in three places: `_check_llm_health`, `_build_llm`/`_FallbackGroqLLMService.get_chat_completions`, and `_build_openrouter_llm` (same param, since `reasoning_effort` is a property of the gpt-oss model itself, not Groq's hosting of it).
- **`reasoning_format: "hidden"` (Groq) / `extra_body={"reasoning": {"exclude": True}}` (OpenRouter)**: without these, gpt-oss embeds its raw chain-of-thought directly in the same `content` field as the actual reply — confirmed live on both paths independently (Groq: `"User wants to confirm booking. We need to finalize..."` spoken as part of a reply; the OpenRouter equivalent was added 2026-07-27 as defense-in-depth for the same model reached via the last-resort fallback below, though the specific live incident that prompted adding it turned out on inspection to have gone through Groq directly, not OpenRouter — see `max_completion_tokens` below for what that incident's real cause was). Must go via `extra_body`, not a bare kwarg — the OpenAI/Groq SDK's typed `create()` doesn't recognize either param name directly and raises on every call if passed bare.
- **`max_completion_tokens=400` (Groq)**: added 2026-07-27 — the Groq path had **no token cap at all** before this. Confirmed live: a single completion on a long, noisy (mixed-script, low-signal) call came back as 3072 completion tokens (the same clarifying question paraphrased dozens of times, some of it degenerating into a flood of near-empty fragments) versus a normal reply's tens of tokens. `reasoning_format="hidden"` was working correctly on that same completion (a small, separately-reported reasoning token count) — this was the model's actual answer content degenerating into repetition, not a reasoning leak. 400 gives real headroom over any legitimate single turn while bounding how much a degenerate completion can ever generate; see `app/voice/repetition_guard.py` (Pipeline stages above) for the complementary guarantee that none of what's generated repeats.
- **Last resort**: if every model in `settings.groq_models` is marked down in `llm_health`, `_build_llm()` falls through to OpenRouter (`_build_openrouter_llm`, `OpenAILLMService` pointed at `https://openrouter.ai/api/v1`, `max_completion_tokens=900` — capped because OpenRouter's free-tier credit check rejects based on the *requested* ceiling, not actual usage).
- **Exposed at**: `GET /api/v1/health/llm` — read-only snapshot of `llm_health`, for a dashboard widget.

## Turn detection strategies

Config: `TURN_DETECTION_STRATEGY` (`vad_fixed` default / `hybrid_experimental`) — experimental, `shagun` branch only, deliberately not in `render.yaml`; `main`/production is unaffected regardless of this setting.

- **`vad_fixed`** (production default): `SpeechTimeoutUserTurnStopStrategy(user_speech_timeout=0.9)`. 0.9s is the validated middle ground — 0.6s cut guests off mid-thought, 1.4s added ~1.4s of dead air per turn.
- **`hybrid_experimental`**: `app/voice/turn_strategies.HybridCompletenessUserTurnStopStrategy(base_timeout=0.9)`. Runs a fast, local, non-LLM heuristic (`_is_incomplete`) on the accumulated transcript when the base 0.9s timeout fires: trailing conjunction ("and", "but", "aur", "और", determiners/prepositions like "the"/"in"/"that"), trailing comma, or a short (<3 words) unpunctuated utterance → extend the wait once by `extension_timeout=0.7`s, up to a hard `max_wait=2.8`s cap measured from the original VAD-stop moment. Falls back to identical behavior to `vad_fixed` if the transcript looks complete. No spoken filler is used during the extension — an earlier version tried `TTSSpeakFrame` push from the strategy itself, but confirmed live that this isn't ordered against the main LLM→TTS flow and could corrupt an in-progress reply.
  - **Known gotcha, already fixed**: pipecat's transcript can arrive *before* `VADUserStoppedSpeakingFrame`. Without an explicit fallback (`_handle_transcription`'s branch for `not self._vad_user_speaking and self._vad_stopped_at is None`), the strategy's timer chain never starts, and the turn only ends via pipecat's generic ~5s stuck-turn watchdog (`strategy: None` in logs), not the intended adaptive behavior.
  - `[DEBUGTURN]`-prefixed debug logging is intentionally still present for live verification; safe to strip once confirmed working end-to-end on a real call. Grep the backend log for `strategy:` to see which class actually fired for a given turn.
